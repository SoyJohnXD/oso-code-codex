# Shared Engram memory

Engram is Oso's normal shared record for preferences, decisions, plans, diagnoses and outcomes. Use this protocol when starting, resuming, checkpointing or finishing an Oso workflow. It preserves the topic keys used by Claude Code and OpenCode. Product files remain the code; the ignored `.oso-code-codex/` directory holds technical execution evidence. Do not create operational Markdown plans, ledgers, handoffs or reviewer-report files in the project.

## Project and recall

Resolve the actual task repository, then inspect `mem_current_project`. An MCP server can start in the user's home directory; that result is not necessarily the task project. When needed, register the actual native session with `mem_session_start(id, directory: actual_repository)` and use the returned project explicitly on every search/save. Preserve an existing project identity across hosts and worktrees. A separate fork is a separate project unless the user establishes another mapping. A similar-name suggestion does not authorize moving another project's memories. On ambiguity, use the tool's actual recovery choices rather than inventing a project or silently falling back to personal scope.

The recoverable route is the absolute project, runtime run id, literal Engram topic and actual approval reference. Planning records the first three and waits for a future approval reference; approval or an authorized resume binds the fourth. An old plan can be recovered from this route, the current directory, its executable specification and the actual authority. A known Git base or saved position assists recovery but never becomes another gate.

For plan/roadmap, search this project's `oso/index`, then fetch the selected observation with `mem_get_observation(id)`. Search previews are incomplete; read full content before relying on or updating a record. Locate the requested change, its literal topic keys and `NEXT:` position. Fetch its ledger and plan; fetch the summary when it explains completion or a stale index row. If the index is absent, search the requested `oso/{change}/plan` or `/ledger` directly. Inspect only relevant rows, not every historical change on each turn.

ID-only reads and updates target the observation found by that project-scoped search. Their response envelope may still describe the server's default cwd; verify the actual observation's project/topic and do not silently switch projects from that envelope.

Read `oso/preferences` once per working context and apply established explanation, teaching and autonomy preferences. Preserve host-specific model settings; a Claude model profile is not permission to change Codex's principal model. Quick/debug/quality-pass use established preferences without an extra question round. Debug also searches `oso/{bug}/diagnosis` before diagnosing the same failure again. On resuming a short task, read its known summary/checkpoint and existing runtime record.

After native compaction, use Codex's supplied continuation and recover only missing or stale decisions/position. A new session performs the relevant recall and reconciles it with the local run and Git. Do not add automatic session/compact hooks or rerun completed investigation because compaction occurred. Engram supplies semantic continuity; another host's session handles and successful-check claims cannot become live Codex handles or current executed evidence. Every execution entry starts or resumes its authorized runtime before product edits, reconstructing only an unavailable record; a missing indispensable identity or authority remains a precise pending item.

## Compatible records

Keep the same project scope and topic keys when continuing existing work. Use a stable change/bug slug from the existing record, not a new slug for each session or agent. Rich titles start with the literal topic key followed by a searchable description. Preserve existing language; new Oso titles/content are English and user-facing explanations follow the user's language.

| Topic | Contents and update point |
|---|---|
| `oso/preferences` | Existing operator preferences and dated changes. Create only from known preferences; preserve unrelated and host-specific fields. |
| `oso/index` | Plan/roadmap discovery, descriptions, status, literal topic references, explicit pendings and `NEXT:`. Update the affected row at freeze, meaningful progress, pause and completion. |
| `oso/{change}/ledger` | Intent, surface map, scope, decisions with rationale and authority, verification/environment requirements, autonomy and dated amendments. Save at freeze; preserve prior decisions when amending. |
| `oso/{change}/plan` | Approved slices/dependencies, acceptance criteria, completed/pending work, actual change base/branch, current position and next step. Mark a slice complete after its required review and delivery action. |
| `oso/{bug}/diagnosis` | Observed/expected behavior, reproduction evidence, root cause, fix decision and named regression or justified limitation. Save before implementation; merge a corrected diagnosis with its history. |
| `oso/{change}/summary` | Decisions, observed outcomes, verification scope, unresolved findings, delivery boundaries and next step. Save at completion or interruption; short workflows use this without manufacturing a full ledger/plan. |

The index retains the compatible status vocabulary `planning`, `executing`, `done`, `roadmap`. A blocked plan remains `executing` with its exact blocker and next step, never `done`. A roadmap row stays `roadmap`, lists children by literal `oso/{child}/plan` keys in order, and states whether work remains. Its ledger holds the queue, global/child decisions and each child's disposition. Update the existing child topics and parent position as work advances; do not duplicate the parent's approval for each child. Quick/debug do not create artificial plan rows in the index.

A parked plan also remains `executing`. Record its retained block, reason, selected independent work and return link. Preserve that row when advancing another plan; parked is never completed. Runtime state governs local execution and pending integration, while Engram preserves decisions and actual authority. Reconcile conflicts explicitly instead of allowing a stale memory entry to reset the runtime.

At completed slices, material recovery decisions, pauses and closure, preserve the recovery owner, effective policy/source, any explicit limit, consumed corrections, finite remaining allowance, current revision, pause reason, actual strategy and `NEXT:` in the existing plan/index/summary. Copy runtime values; distinguish unlimited AUTO from legacy absent policy. Preserve actual adoption authority and later time, money or correction limits. New AUTO roadmap descendants share their root owner, while preexisting durable finite child owners remain separate until each explicitly adopts. Shared memory explains authority across hosts; it does not reset local rounds, invent permissions or replace current executed evidence.

Save the full accepted planning content, including decision rationale and acceptance criteria, rather than a link to a private file or a short summary that another host cannot execute. Supply relevant decisions to children in their assignment; they can use read-only Engram lookup for missing context. The principal owns semantic writes for the whole run, including findings returned by specialists.

## Save and update

Use the native Engram MCP tools. Search before creating a topic. Create an absent record once with `mem_save(project, scope: "project", topic_key, title, type, capture_prompt: false, content)`. Use `architecture` for ledger/plan/diagnosis/index and an appropriate type for preferences or outcomes. Retain the returned observation ID.

For an existing record, read its full current content and call `mem_update(id, title, content)` with the complete merged document. **`mem_update` replaces content; it does not merge it for you.** Preserve other index rows, completed slices, user decisions, dated history and unknown fields. Keep the index's rich title/count and `NEXT:` consistent. A long-lived cached copy is insufficient for a shared index: fetch the current observation immediately before modifying it. If a response is uncertain, read that observation once to determine whether the change landed before attempting another write.

Serialize writes within the run and use one active writer per change. Another host may update other changes; merge those rows. If the same decision changed concurrently, retain both facts and resolve the actual ownership/decision conflict before overwriting it. The exposed update tool has no compare-and-swap parameter; do not claim atomic cross-host merging. If a tool returns `judgment_required`, inspect its candidates using the available judgment tools. A related memory is not a reason to rewrite the same topic repeatedly or restart implementation.

Persist at semantic boundaries: frozen decisions, accepted plan, completed slice/roadmap child, material amendment, actual blocker/pause and final outcome. Coalesce related changes into one update per affected topic. Do not save every tool call, clean verifier repetition or progress message. A review format correction does not justify a new memory topic or verifier.

At completion, update the plan and index to the observed final position, save/update the summary and submit one `mem_session_summary` for the actual session when available. An in-progress summary names remaining work. Native MCP success establishes a local memory write; cloud replication requires its own evidence. Do not claim that a cloud warning prevented a successful local save, or that a local save proves cloud synchronization.

## Continue a plan from another host

Recover its existing project, index, full ledger/plan or diagnosis and relevant summary. Preserve the authored decisions and completed work. Compare the recorded branch/change base, source and acceptance criteria with the actual checkout. Explain the recovered position briefly and continue the remaining authorized scope; do not rerun planning questions that are already answered.

The user's request to execute an already approved plan supplies current execution authority for that scope. Preserve the original approval as provenance; do not fabricate an approval message, import an old green flag or modify another host's runtime files. Start a Codex run for the remaining work, or resume the existing Codex run if present. Keep its technical run ID associated with the same Engram change, even when they differ. On a different machine, retain the recorded recovery counts and unresolved findings in the handoff; moving hosts never grants a fresh repair budget. Reconcile completed portions from code/Git and run the checks needed for current acceptance. Cumulative review still covers the complete intended change.

Inspect actual applicable standing authority before changing recovery policy. If it covers AUTO adoption for this scope, use the explicit local adoption operation in [correction recovery](correction-recovery.md) without asking again. A remembered AUTO preference alone does not replace an older host's explicit NORMAL disposition or a newer limit. Preserve those boundaries and the full policy/authority history in the existing topics. Plugin installation and fresh-thread recall do not themselves migrate project records.

Save the recovered execution position back to the existing topics so Claude/OpenCode can continue later. Include sufficient semantic scope, remaining work, actual evidence references and limitations; another machine may not have local logs. Revalidation of unavailable evidence is explicit, and already implemented code is not automatically reimplemented.

## Memory outage

A failed lookup is not an empty project. Inspect the actual MCP error once; do not create duplicate topics after a failed search, switch projects or bypass MCP through the Engram database/CLI. Reconcile useful locally available context and continue independent authorized work when it remains unambiguous.

For an undelivered write, preserve the intended content, project, topic, known observation ID and error in the single ignored `.oso-code-codex/memory-pending.json` recovery queue. Use `oso-codex memory pending` to capture `position` before composing the semantic update. After a failed MCP delivery, `memory queue --file -` accepts `{ "project": "shared-project", "topic": "oso/change/plan", "observationId": 123, "position": { "runId": "actual-run", "revision": 12, "recoveryRevision": "returned-family-revision" }, "content": "full current merged document", "error": "actual MCP failure" }`. Copy the entire observed position, not this example or a manually reconstructed subset. `recoveryRevision` detects family budget/strategy/progress changes even when the selected child's lifecycle revision is unchanged. Without a run the returned position has revision zero and no run ID. If that topic already has a queued entry, read it with `memory pending --full`, merge its decision history, and supply its current `id` as `previousId`. Old lifecycle or recovery revisions cannot overwrite newer state; superseded content remains recovery history. This is an emergency delivery cache, not a second planning system or a new Markdown document. Keep the actual next step in the runtime note when a run exists. Do not retry the same unchanged outage at every slice or replace the agent.

When service availability changes, read current observations and the local position, reconcile the latest semantic state, and deliver once. A `stale` pending entry must be recomposed at the current position; never replay its old park/resume/close event over later work. After actual native MCP acknowledgement, `memory delivered --file -` accepts `{ "id": "exact-delivered-entry-id", "evidence": "actual MCP result" }` and removes only that revision. A late acknowledgement cannot remove its replacement. The runtime never calls MCP or proves cloud delivery itself. Preserve unrelated pending entries and local execution evidence. A missing plan or conflicting authority can block dependent work. A memory outage does not erase the code already completed, and an outstanding shared-memory handoff must be reported as pending. Never present cross-host continuity as synchronized while its write remains undelivered.
