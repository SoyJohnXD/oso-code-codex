# Runtime recovery and parked plans

Read this reference only for an actual failure, interrupted process, preserved-work reconciliation or change of active plan. Ordinary checks and reviews use [runtime](runtime.md).

### Park an approved plan

Use `status --transitions` to inspect available transitions and their concrete prerequisites. This command is read-only, including while a run is open; it does not acquire the execution transaction lock or freeze another decision.

Use `park --reason "next independent objective"` when changing focus. Reconcile every running or uncertain check and native agent first. Parking preserves the run ID, selected block, approval, original baseline, reviews, findings, correction rounds and permission episodes. A parked run stays explicitly selected until another authorized run is chosen; parking never deletes the selector to disable the harness. Checks and code edits cannot execute against a parked run.

For a clean checkout, start the separate approved objective with `start --from-run PARKED_ID --file - --authorization -`. Supply its actual specification and existing user authorization. A new run is appropriate for a distinct objective, never for repairing the same failed scope with a renewed budget. Same-checkout delivery boundaries remain binding across the linked runs. If the checkout contains partial work, use the isolated integration route below; do not stash, manufacture a WIP commit, reset or relabel the active block as a bridge.

After the separate run has its reviewed closure and commits, `resume --run PARKED_ID` reconciles its contribution. The runtime records source run/specification, reviewed checkpoints, commits, exact file hashes and Git modes, including deletions. Only that proven external delta contributes to the effective ownership baseline. The original run and block baselines remain unchanged; unrelated or later unreviewed changes cannot be absorbed. A's checks must still match A's current fingerprints and required criteria. B's green result is not imported as A's evidence. Review A's cumulative changes and interactions with B, and amend only if B actually changes an approved decision.

An authorized amendment may insert prerequisites before a selected block that has not actually started: no source or mode changes, check attempts, reviews, findings, repair rounds, failure or agent assignment. The untouched block retains its ID and history and returns to pending so the new predecessor can execute. A selected block with work or evidence must be parked or completed according to its actual state.

Existing version1 records remain readable. A lifecycle transition requiring these semantics promotes them to version2 with its minimum reader version; later versions never downgrade on resume. Explicit external fulfillment below requires v4 even without AUTO. Truthful coordination and contribution accounting require v5. Only new create, authorized amendment or supported reconciliation promotes atomically to v5; ordinary read/install does not migrate a record, and older readers reject it. Engram remains semantically compatible across hosts, but that does not make an older runtime understand new lifecycle fields.

### Reconcile a legacy roadmap child

`oso-codex roadmap reconcile --run PARENT --child CHILD` is the single supported route for a legacy child lineage. It requires the exact durable parent origin, actual current authorization and a complete additive ordered-prefix amendment chain. A replacement that changes or removes an original dependency does not fulfill that original obligation. Ready independent siblings can continue. The command preserves the legacy history and records its promotion; it never invents a past approval, and read/install alone does not reconcile anything.

### Isolate B while preserving partial work in A

After parking A and reconciling its handles, create a separate Git worktree and branch from A's recorded HEAD for the independent approved objective. From B, use `start --from-run A_ID --from-project /absolute/A --file - --authorization -`. The runtime verifies that both worktrees belong to the same Git repository and records their link. The principal retains ownership of coordination; native filesystem permissions still govern access to the shared records.

Complete B's scoped checks, independent review and commits in its own worktree. Then, from A, use `integrate --from-run B_ID --from-project /absolute/B`. Only reviewed committed content, modes and deletions may become the external contribution. A linear, disjoint contribution can fast-forward A while preserving A's existing staged and unstaged work. Named check resources coordinate across the linked worktrees; each checkout keeps its own execution bar.

Before Git integration, the runtime persists its intent with source identity, reviewed commits and expected before/after state, including the index. If interrupted, repeat the same integration command: an unchanged initial state can execute the recorded action, the expected already-integrated state can finalize its provenance without replaying Git, and a divergent state requires reconciliation. A native permission denial remains a real boundary; never substitute a different wrapper or Git operation to evade it.

An overlap with A's partial work or an incompatible history leaves B complete with integration pending. Preserve both worktrees and report the concrete conflict. A can resume its unchanged work with that pending integration recorded; no contribution is imported until verified. Resolve the actual conflict within the approved decisions, then integrate explicitly. Never discard A's index or claim that pending integration is complete.

### Record explicit external fulfillment

When reviewed work in B satisfies A's selected block, resume A after its contribution is imported; an isolated contribution must be fully integrated first. Inspect the selected source checkpoints and A's acceptance criteria. Run A's own required current checks and obtain its independent acceptance review. Record that review without `--finish`, then submit `oso-codex checkpoint --file -`:

```json
{
  "block": "selected-a-block",
  "targetSpecDigest": "current-a-specification-digest",
  "sourceRun": "imported-b-run",
  "sourceSpecDigest": "imported-b-specification-digest",
  "sourceBlocks": ["reviewed-b-checkpoint"],
  "evidence": "The concrete rationale connecting these source checkpoints to A's accepted behavior"
}
```

Use exact recorded identifiers; `sourceBlocks` must be nonempty and unique. The runtime resolves B's project from retained successor or isolated links, not a supplied path. B and the selected checkpoints must be closed, with intact independent review, criteria, snapshots, Git modes, explicit deletions and executed check logs. Historical check evidence may belong to B's exact authorized roadmap family; it is not copied into A.

The selected source scopes must conservatively cover A's complete block scope, including wildcard coverage. A's current files, modes and explicit deletions must match those closed checkpoints and the imported contribution. The recorded before-to-after commit interval must equal the contribution's commits, and its after head must remain an ancestor of A's current HEAD. Missing, partial, stale or tampered evidence fails before any state mutation. An unavailable historical review, log or source worktree is a specific provenance gap, not permission to infer completion from block names.

A still passes every normal `closeBlock` prerequisite: current required checks covered by its own independent acceptance review, no unresolved failure or finding, reconciled agents and authorized scope. Closure records `status: closed` with `externalFulfillment`: source project/run/specification and selected blocks, contribution and source-evidence digests, target specification digest, A acceptance-review ID, rationale and time. `externalFulfillments` retains the history. Original baselines, approvals, findings and correction history remain intact; remaining A blocks and its cumulative review still need completion.

Exact payload replay while that checkpoint and its provenance remain current is a no-op with no new event or JSON write, including after A's final closure. Conflicting mappings fail unchanged. Reopening removes the active claim but retains its history; replay cannot restore the reopened claim. A later ordinary local checkpoint remains locally closed with historical fulfillment preserved. Plain `checkpoint` is still available when no external mapping is being claimed.

### Resume failures and preserved evidence

`resume` reconciles persisted processes and gives the next step. It never replaces a still-running command. For native children, use the native tool to inspect/wait on the recorded handle before replacement. A local record does not imply a child stopped. `status --full` provides the complete spec, findings and evidence inventory; ordinary status is concise.

Resume the existing run and Engram position before reconstructing anything. Reconcile preserved approved files through adoption when necessary; existing user authority can supply the actual authorization record without asking again. Do not reset the baseline or recreate a run to make ownership disappear. A registration mistake is corrected from the actual delivered review and assignment; request focused confirmation from the same reviewer only when substantive coverage is missing. A native approval timeout is a delivery boundary, not a product test failure; preserve passed evidence and use the native approval route once there is a concrete action to approve.

Fingerprint version 2 records effective executable identity and explicit internal helpers. Older opaque fingerprints cannot establish that provenance and remain historical evidence. When current evidence is needed, reopen the affected existing block, execute its required checks once, and let the existing reviewer confirm the new results. Preserve the old logs, approval, findings and correction budget. Never rewrite an old fingerprint, manufacture a pass, or launch repeated suites to diagnose this known format transition.

Codex commands can run in separate PID namespaces. The runtime conservatively treats a process in another namespace as unresolved, never as dead from its local PID absence. If the native command handle confirms that the runner and all its children ended without a recorded final result, use `resume --stopped-check ATTEMPT --evidence "actual native terminal result"`. This retains partial logs, records an infrastructure failure and releases only locks owned by that exact process identity. It does not create successful check evidence. Never attest a live or uncertain handle as stopped.

Command/review failures record an episode automatically. Other gaps use `failure --kind infrastructure|delivery|product|decision --cause TEXT`. Inspect `recovery status` and load [correction recovery](correction-recovery.md) for AUTO progress, actual strategy checkpoints, finite grants and explicit legacy adoption. On resume, existing standing authority can authorize adoption without another user question when its scope covers that change; preserve later explicit limits and other boundaries. After readiness permits repair and the cause is fixed, prefer `check ID --retry --evidence TEXT`; add `--measured TEXT` for actual changed-environment/delivery evidence. It records recovery and prepares the check atomically, without first attempting a command that the known failure would block. Standalone `retry --evidence TEXT` is still compatible. A note or `--escalated` alone never clears a failure or proves diagnosis.

For a linked permission failure, inspect the native error and the underlying command's access needs. If native approval resolves that cause, submit `check ID --retry-permission --evidence TEXT` through the native approval route. Explain that exact command and access in the native justification. Supply truthful evidence of that invocation's native authorization, never a fictional receipt. Oso records supplied evidence only after Codex allows the process to start; the flag does not request or grant access. Native denial or timeout leaves the runtime unchanged and must be reported without an automatic retry loop.

Permission recovery is one attempt per unresolved check episode, separate from correction consumption. It may finish verification of the last authorized cycle at zero remaining, but cannot authorize another code correction. If it fails again, preserve the episode and diagnose the actual cause; a changed label/agent/session or standalone retry cannot renew it. Older passing evidence cannot close an unresolved access failure even when its inputs match; a new successful execution resolves the episode. Legacy records without linked permission evidence keep the ordinary correction route; no historical permission grants are invented. Access diagnostics including EROFS are infrastructure, not product failures, and a mention of an error code alone cannot authorize recovery.

Both combined recovery flags target a single check ID. They cannot be combined with each other, `--all` or `--red`; permission recovery also excludes `--measured` and `--escalated`. On a failed execution the JSON result includes the next action, along with the original log and diagnostics. Continue other checks through the normal runner after the affected check succeeds, reusing current evidence.

`finding --file -` records `id`, `rule`, `evidence`, `disposition` (`open`, `fixed`, `false-positive`) and an evidenced `resolution` for a closed claim through stdin. Keep optional submission files and full analysis output inside the ignored runtime directory; do not leave evidence JSON in the product scope. No residual waiver exists for a real rubric violation. `note --next TEXT` preserves the next concrete action/resource owner. `amend --file SPEC --authorization APPROVAL` records a genuinely authorized material change while retaining existing block ids, findings and budgets.

If a required commit or publication fails after a reviewed checkpoint, record `boundary --action commit --cause "observed native permission failure"` (or `publication`). This run-wide boundary prevents the same action from retrying in later slices and prevents final closure. Continue independent authorized code work when appropriate. Resolve with `boundary --action commit --resolved --evidence "actual native approval or completed-action result"` only after the cause changes through the legitimate native route. The boundary retains two ordinary recoveries and one justified `--escalated` recovery across slices. A note or changed label does not clear it. Never bypass a denied action using a different wrapper or external writer.

`import --file LEGACY` reads legacy provenance without changing its source, importing approvals or converting a claimed old green flag into current check evidence. Reconcile useful historical decisions explicitly against the current authorized task.

When resuming approved work that already existed before this run started, `adopt --file - --authorization -` accepts `{ "files": { "src/example.ts": "current-sha256" }, "authorization": { "kind": "user", "reference": "actual-native-message-reference", "message": "actual user authorization", "specDigest": "current-specification-digest" } }`. Include only the explicitly reconciled files in the approved scope. Each must remain identical to the original run baseline and have a pending Git change. The runtime records exact hashes, Git file modes and authority without rewriting that baseline, checks, reviews, findings, budgets or delivery boundaries. Mode changes against the original Git head and new executable files or symlinks cannot be adopted. It cannot authenticate prose as human approval; use the actual native user authorization. Adoption alone never authorizes an unreviewed commit or resolves a boundary. Changed source still needs current checks and review, and a staged adopted version must match the reviewed worktree and recorded mode.

Hooks guard ordinary edits, commit readiness and publication intent while a run is active. Shell checks inspect command positions, explicit shell wrappers and command substitutions; quoted arguments, test bodies in heredocs and comments are data. They deliberately do not interpret arbitrary application scripts, dynamic commands or every shell dialect, or treat unknown tools as memory mutations. Native permissions remain authoritative. A combined commit-and-push request must satisfy both boundaries. Hook execution requires Codex hook trust.

If runtime startup fails, inspect the specific error once. `Hook failed` with exit 1 indicates a process failure, not a successful quality verdict. After an update, check whether the thread references a removed cache or an incompatible reader; preserve the continuation and use a fresh thread with the installed compatible payload. Installation never migrates project records. Do not disable the hook, modify native cache files or downgrade retained v3/v4 evidence. A protected-action validation error returns an explicit deny with its original cause; read-only diagnosis remains available. A native permission denial uses the native approval route; if unavailable, report the exact blocker. Do not try many shell wrappers or launch another verifier. The metadata capture uses file-backed stdio to retain actual output under Codex; errors are never ignored.
# Delivery recovery

An open delivery boundary still limits retries: record fresh authorization or changed permission evidence with the ordinary boundary resolver, preserving every prior round. Do not use completion reconciliation to attempt Git again.

When an isolated Git integration was already completed outside the interrupted native call, `boundary --action commit --resolved --completed-integration RUN --evidence TEXT` is a verification operation. It accepts only the durable integration operation record, its registered external contribution, the exact immutable Git interval, and retained ancestry. It records a completion receipt without adding a retry round. It does not alter later commits, staged files, or pending work. Older records without structured operation identity are accepted only when their retained intent, failed delivery, and finalization event sequence proves the same source operation.
