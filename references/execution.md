# Execution contract

Preserve the full [rubric](rubric.md); reducing coordination must not reduce the quality bar. Read the [runtime instructions](runtime.md) once when starting or resuming execution.

## Authority and scope

Use the actual user request/approved plan as authority. The executable authorization tuple is the absolute project, run id, literal Engram topic and actual approval reference. A future approval reference cannot exist while planning: bind it only when the user approves or execution resumes. A known base or position helps recovery but is not an additional authorization gate. Recover an older document route from the current working directory, Engram, the executable specification and the actual authority.

Every plan, roadmap, quick, debug and quality-pass entry starts or resumes its authorized local runtime before product edits, reconstructing it only when the local record is unavailable. If indispensable identity or authority is missing, preserve the precise pending item; do not make a detached implementation. A precisely specified roadmap child inherits its parent's recorded authority. Material changes to scope, contracts, cost, irreversible actions or permissions require the user's decision. Native Codex sandbox and approvals remain authoritative; never disguise a denied action with another wrapper or tool.

Inspect the baseline and preserve unrelated changes. Keep the approved decisions and observable acceptance criteria in the local run. Amend a material decision with the user's actual authorization; never relabel a code defect as a decision change.

For new approved AUTO work, record `recovery: {"mode":"auto"}` without an arbitrary correction ceiling. Preserve any explicitly authorized `maxCorrections`, time, money and external-action limits. On resume, inspect the existing runtime policy and applicable standing authority; use [correction recovery](correction-recovery.md) to adopt AUTO when already authorized, without another permission question. An old finite or absent policy stays unchanged until that explicit operation. NORMAL and other-host boundaries are not silently converted to AUTO.

New code, identifiers, diagnostics, tests and technical documentation default to English, following the project's established conventions and approved contracts. Preserve the chosen language of UI copy and public routes. This is guidance for the authorized change, not an instruction to rename existing code or translate a product without approval. User-facing conversation follows the operator's language; technical artifacts and delegated assignments do not inherit a conversational persona.

## Implementation and delegation

Work sequentially by default in the existing checkout. Each bounded applier assignment states its outcome, frozen decisions and invariants, owned files/scope, relevant environment, affected checks and what constitutes done. Supply existing evidence and identify concurrent owners so the child can preserve their work. There is no mandatory applier/integrator/triage relay: the principal can make a small understood fix and resolve a clear integration conflict.

Delegate substantial separable investigations and implementation assignments when they keep noisy exploration or an independent body of work out of the principal's context. Keep bounded edits, shared decisions and integration with the principal when delegation would add little. Supply scoped context rather than the full conversation, ask for concise findings with source locations and consume them without repeating the child's investigation. A compacted context is a continuation mechanism, not a reason to retain unlimited logs or re-read completed work. No percentage-of-context rule or mandatory explorer count governs a small task.

Keep Codex's native compaction and continuation intact. Add no session/compact hook, context threshold gate or automatic post-compaction work. Use the continuation already provided; retrieve only missing or stale decisions and position. Discover tool names first, load only selected schemas, and project large results to relevant counts, findings and source locations before returning them to the model. Retain complete evidence locally when needed for review. Load recovery instructions only for the corresponding recovery, and do not reread references already available in the working context.

Every assignment carries the native permission boundary and delivery rule directly, including when a generic native agent is used instead of an installed role: stop a denied action, report its actual error immediately, and return completed source even if commit/integration is blocked. No alternate Git plumbing/index/git-dir/cwd, scratch export or wrapper may bypass the denial. Do not repeatedly tell a blocked applier to complete the same command; the principal records the shared delivery boundary and uses the legitimate native approval route.

## Model selection and escalation

Keep the model the user selected for the principal. The principal owns decisions, integration and closure. Small, already-understood fixes may stay local; delegate substantial implementation, investigation and corrections unless the work is too coupled or a truly bounded local edit is cheaper. Choosing Astra for the principal does not change a child's Luna default; only an explicit model preference for that child or scope overrides it. Never silently substitute a higher tier when a requested model is unavailable.

Start each independent delegated task with `gpt-5.6-luna` at `max`. Set both `model` and `reasoning_effort` explicitly, with `fork_turns: "none"`; an explicit user choice for that assignment overrides the default. Keep role TOMLs unpinned so the native launch carries the model and effort. Luna assignments are small, closed-decision tasks with concrete inputs, provider errors, expected outputs, focal checks and a done condition; the agent has strong autonomy within that frozen contract. The same quality bar applies to every model.

The approved specification may set `coordination.maxActiveAgents`. It counts native child agents, not the principal. Inspect native total capacity, current live children and ownership before choosing that approved limit. A v1–v4 record without coordination retains the policy limit of two. Do not invent coordination after approval, and do not retrospectively inject a configuration digest into an old run. Preserve writer-overlap protection and check/resource locks; this policy adds no scheduler.

An approved optional `reviewFallback` is a complete actual model/effort configuration. If the principal cannot identify an approved fallback, preserve that pending reviewer constraint. A successful native launch with the requested model, effort and `fork_turns: "none"` is sufficient requested configuration; later host facts are current observations, recorded separately. Old review records remain historical. `sol` is unranked unless it has the same actual model and effort as the relevant implementation or an approved fallback covers it; never imply Luna coverage from its name.

Use `gpt-5.6-terra` at `high` from the outset only for a concrete critical authorization, security or data risk, a data-loss migration, or complex visual design that requires new decisions. Routine frontend, authentication or multi-module labels alone do not qualify. Otherwise, escalate Luna to Terra only after the initial attempt and two directed corrections on the same problem show no verified relevant progress. Escalate Terra to `gpt-6-astra` at `high` only after the same threshold, and only for a critical unresolved problem; allow one justified Terra-to-Astra escalation per problem, without introducing a global correction ceiling. A one-off delivery may choose Terra/high without changing this permanent default. Briefly explain an initial Terra exception or escalation with evidence in the existing run/review record.

Verified relevant progress resolves an acceptance criterion, substantive finding or evidenced measure. Rereads, added prose and unchanged green checks are not progress. Permission, tool and infrastructure errors are not model incompetence and do not justify model escalation.

Reuse the same agent for directed corrections when its model is sufficient. Decide on escalation at the next correction boundary before registering an agent for the current failure. If native follow-up cannot change the model, first reconcile the prior native result and confirm no writer is still running. The prior assignment belongs to its completed round; after two corrections without progress, the principal records the actual changed strategy through [correction recovery](correction-recovery.md) before registering the next model tier. Do not bypass the runtime's duplicate same-failure role gate by changing identity, retrying or relabeling; if it is still occupied, preserve the boundary and use supported recovery. Once permitted, transfer only the remaining scope to a correctly configured agent while preserving the same run, failure, history and budget. Block review and directed confirmation stay at least at that block's implementation tier; cumulative review stays at least at the highest implementation tier used across the plan/change. A runtime review tier records the actual native reviewer model and cannot raise its tier by metadata alone.

Check actual host/model availability before launch. If a requested model is unavailable, report that constraint and obtain an authorized route before substituting another model. Role files must not silently override the explicit native launch.

This is instruction-led model-selection guidance, not an added runtime launch or registration gate.

The child reads and resolves its assignment; it never launches further agents. The native tool starts the child immediately, then the principal serially registers its real id and requested configuration. On registration failure, interrupt the child and reconcile the partial effects; do not silently baseline, reuse evidence or commit. Resolve the resulting assigned/check/review boundary before continuing. Preserve the native result and recover missing substance with a directed follow-up to that same agent. A follow-up retains its original configuration and deliveries. A replacement records the completed same-role assignment it replaces. Reconcile a possibly running writer before replacement; formatting alone is not a reason to launch another.

The principal records an explicit contribution after its own effective work or after a finished applier's delivered assignment. A native contribution is never inferred from launch; observations are recorded after delivery. Keep requested configuration, current observations, assignment scopes, deliveries, contribution evidence and replacement linkage distinct.

For each slice that changes behavior, obtain a meaningful failing regression before implementation where feasible. Establish that the intended assertion fails, not merely its runner or environment. When a failing test would be misleading or unavailable, record the specific reason and use an appropriate observable verification alternative. Never manufacture red evidence after the fix or write assertions that merely repeat the implementation.

A recorded failure does not prevent registering the real native agent assigned to diagnose or repair it. One agent per role may own that unresolved failure; use its result instead of spawning replacements. Checks remain blocked until actual repair and recovery are recorded, either with ordinary correction or the single native-authorized permission recovery below. Exhausted correction budgets prohibit further applier work.

Use worktrees only for genuinely independent writes that warrant isolation. Record their paths, branches, native owners and integration status in the run's next-step/event notes. Keep the original tree/branch until its work is integrated and verified. Resolve routine conflicts against the frozen decisions, validate affected contracts, and use `git worktree remove` / `git branch -d` only for this run's safely integrated resources. A refusal may protect unique work; inspect it, never force-delete. Ordinary verification does not require exporting a scratch checkout.

## Executed evidence and independent judgment

Run each approved command through the one check executor. Its record names command, cwd, input identity, environment identity, process, final exit, complete log and diagnostics. An applier's narrative is not executed evidence. Include all relevant source, test, config, dependency and environment inputs when specifying a check; conservative wider inputs are appropriate when dependencies are unknown. Each command uses only its actual service/setup dependencies. Direct commands remain direct; a required setup wrapper belongs only to its dependent checks and is itself a declared input. Check names do not determine dependencies or permission needs.

The runner serializes project checks, including shared ports, databases, cache and build output. It never replaces a running executor. Register native assignments before starting a check, and await its terminal result before another runtime mutation; read-only inspection can continue meanwhile. Do not launch an additional shell copy of a check already owned by the runner. Logs and identities survive interruption and resume. If a real sandbox denial prevents a required command, use Codex's actual approval flow for that command; do not weaken its result or keep repeating it.

Independent review combines behavioral acceptance, the rubric and frozen-decision conformance. The first pass inspects the complete assigned surface and current check records, then batches supported findings and coverage gaps. Address related findings together and request directed confirmation from the same reviewer on the changed contracts. A focused additional probe is appropriate for a concrete evidence gap; a new full suite or replacement reviewer is not required to change report formatting.

Author focal checks, then hold the stable full required verification bar. Establish initial scope, environment and actual dependencies before starting work. Complete the first independent review of the whole assigned surface before editing its findings; batch related corrections. The same independent reviewer performs directed confirmation. Expand independent coverage to the affected full surface when contracts, scope, security or dependencies change. For plan, independently review each slice before committing and perform cumulative debt/conformance review against the original change base. For quick/debug/standalone quality-pass, one combined independent final review suffices. A reviewer never authors the scope it attests. Do not stitch partial child green results or duplicate an unchanged suite; reuse only exact current inputs with intact logs.

For a visible change, the approved plan names states, interactions and viewports. The principal prepares the app and data once. After the change, the author records an actual current observation and a distinct reviewer records a current render and critical interactions. Each ordinary report names build/code, URL, viewport, data, observer and artifacts. Earlier screenshots and author prose are not independent observation. If the required capability is unavailable, preserve the exact missing visual criterion as pending. Use existing browser tools and reports; do not create a universal third design review or a backend visual schema.

Reusing evidence requires identical relevant inputs and intact successful logs. Source, tests, config, dependency or relevant environment changes invalidate their dependent checks. A report's spelling, resume, message, commit with identical content, or unrelated documentation edit does not. After a fix, rerun affected checks and request directed confirmation from the same reviewer. Stop repeating checks once the required evidence is current and no unresolved concern warrants another probe.

## Failure and correction

Distinguish product defects, infrastructure/permission failures, delivery/evidence gaps and material decisions. Preserve actual warning output. `INFO`, `NOTICE` and update banners are not warnings by their presence alone; verify their substance. Never suppress an actual diagnostic to obtain a pass.

Read [correction recovery](correction-recovery.md) for an actual failure or policy adoption. `recovery status` determines readiness under the retained policy. AUTO has no implicit correction-count ceiling: two corrections without qualifying relevant progress require autonomous diagnosis and a changed `recovery strategy`, not permission to buy more attempts. An explicit ceiling remains binding. `recovery adopt` applies actual AUTO adoption or policy-change authority; `recovery authorize` remains the finite-grant route. Both preserve the existing run and evidence. Repair the cause before retrying. Prefer `check ID --retry --evidence TEXT`, adding `--measured TEXT` for actual changed environment/delivery evidence. It records recovery and prepares the affected check in one transaction; an invalid target, busy executor/resource or failed log preparation cannot spend a correction. Existing standalone `retry` remains supported. The same unchanged cause cannot relaunch a check or an agent.

A permission is an access decision, not a code correction. After an observed linked access failure, inspect whether native authorization actually resolves the cause. Submit the exact `check ID --retry-permission --evidence TEXT` invocation through Codex's legitimate approval route, with the check, underlying command and needed access in its justification. The evidence describes the actual native authorization of that invocation; the runtime records it only if the host lets the process run. It cannot prove or grant native permissions itself. A denial or timeout authorizes nothing: preserve the blocked work and report the native outcome without another automatic request.

That route allows one retry per unresolved check permission episode outside the correction budget, including completing the last authorized cycle at zero remaining. A repeated access failure retains the episode across sessions, agents and standalone retries. Diagnose it and use a measured ordinary repair or report the missing permission; never relabel, amend or replace state to get another free attempt. Other infrastructure failures and legacy failures without linked evidence use ordinary correction. An unresolved access failure invalidates older passing evidence even if its inputs match: only a new successful execution resolves that check's episode. Historical attempts/events remain. A permission flag grants no correction units or authority to edit a new failure at zero remaining.

An unchanged environment failure also remains known across slices. If a required commit/publication is denied after checkpoint, use the runtime's run-wide delivery boundary; do not repeat that action on the next slice. Its native approval or actual completed-action evidence is required to resolve it. Reviewed code can be preserved while the whole delivery remains incomplete.

At an explicit limit or stagnation, preserve work, logs, findings, live resource handles and the precise paused criterion. Diagnose through read-only tools and use the corresponding supported recovery operation. Stagnation within approved AUTO calls for a substantive changed strategy. For a policy change, reuse authority that actually covers it; otherwise present the concrete missing authority or material decision. Do not manufacture a green result, disable the plugin, replace the run or automatically reset its policy. Zero remaining under a finite limit still permits verification and review of the last authorized cycle. Continue separate approved independent work only when dependency and ownership constraints allow it.

Every finding retains its rule/decision, location, evidence and disposition. Fix a real violation. The principal can disprove a false positive with the actual rule and code evidence; it cannot waive a real violation, including an inline-comment violation or a nit. A conventional API doc form or verified builder annotation is governed by the rubric itself, not a new exception.

Record a substantive non-pass review and its findings before editing the correction. For a cumulative finding, reopen the responsible existing block first, then record the non-pass review/failure and actual finding there. After the fix, consume a correction round with evidence and obtain directed confirmation. Do not repair a review finding outside the record: doing so would hide the recovery budget and make a later session repeat the work.

## Closure and persistence

Use [shared Engram memory](engram.md) for the plan, decisions, preferences and cross-host position. The local versioned record retains technical evidence and enforces execution readiness. Only the principal writes either. Update Engram at completed slices, material decisions, pauses and closure; coalesce related semantic changes rather than copying every event. Persist failed deliveries through the bounded memory-outage route. Integrations preserve their applicable criteria as described in [integrations](integrations.md).

Before each commit, checkpoint the reviewed block. Stage only owned changes, preserving unrelated index/worktree content. No manual `verify_green=true` flag exists. Closure is computed from required checks, current review, findings, approvals and completed blocks. A late code fix reopens the same block and retains its budget.

When imported reviewed work from B fulfills A's selected block, use the explicit `checkpoint --file -` mapping in [runtime recovery](runtime-recovery.md#record-explicit-external-fulfillment). A still needs its own current required checks, independent acceptance and normal closure prerequisites. Do not redo already accepted work merely to claim local authorship, infer completion from similar names, or copy B's green state into A.

Progress messages say what was learned or delivered, real findings/blockers and the next step. No punctuation or fixed prose template is a gate. The final report states the resulting behavior, relevant verification, any material limitation and the actual unfinished boundary. Autonomy does not turn an incomplete required check into completion.
